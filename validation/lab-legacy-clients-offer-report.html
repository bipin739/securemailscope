HIGH SMS-TLSVER-001 Deprecated TLS Version (TLS 1.0) Session: SMTP-STREAM-2
Confidence: HIGH

Plain Explanation: Observed email session negotiated deprecated TLS 1.0 protocol, which is susceptible to known downgrade attacks and lacks modern authenticated encryption.

Technical Impact: TLS 1.0 is formally deprecated under RFC 8996 due to lack of modern cipher constructions, vulnerability to downgrade attacks, and security weaknesses.

Remediation: Disable TLS 1.0 on 198.51.100.25 and configure the mail server to require TLS 1.2 or TLS 1.3 as the minimum acceptable protocol version.

[RULE] Recommended fix
  1. Inventory ClientHello offers and upgrade clients that cannot offer TLS 1.2 or newer.
  2. Set a TLS 1.2 minimum on the affected service after staging tests and a rollback plan.
  3. Check both mandatory and opportunistic TLS settings for the intended service.

MEDIUM SMS-PFS-001 Static Key Exchange Without Forward Secrecy Session: SMTP-STREAM-2
Confidence: HIGH

Plain Explanation: The session negotiated a static RSA key exchange cipher suite lacking Perfect Forward Secrecy. Compromise of the server private key allows retroactive decryption of past sessions.

Technical Impact: Static key exchange allows an adversary who captures encrypted traffic to decrypt it retroactively if they acquire the server's private key in the future.

Remediation: Configure the mail server to disable static RSA key exchange suites and prioritize ECDHE key exchange.

HIGH SMS-CIPHER-001 Weak / Deprecated Cipher Suite (TLS_RSA_WITH_3DES_EDE_CBC_SHA) Session: SMTP-STREAM-3
Confidence: HIGH

Plain Explanation: The session negotiated weak or deprecated cipher suite TLS_RSA_WITH_3DES_EDE_CBC_SHA, which is vulnerable to cryptanalytic attacks.

Technical Impact: The selected cipher suite (TLS_RSA_WITH_3DES_EDE_CBC_SHA) utilizes obsolete algorithms (such as 64-bit block ciphers like 3DES vulnerable to Sweet32, or stream ciphers like RC4) susceptible to practical collision or plaintext recovery attacks.

Remediation: Disable obsolete cipher suites (RC4, 3DES, DES, EXPORT, NULL) on the mail server and require modern AEAD suites (e.g., AES-GCM or ChaCha20-Poly1305).

[RULE] Recommended fix
  1. Upgrade the affected mail server and client TLS libraries.
  2. Remove the identified weak suites from that service using its version-specific cipher configuration; prefer supported AEAD suites.
  3. Test client compatibility and verify the newly selected cipher in a fresh capture.

7. Authoritative Limitations & Scope
  • TLS selections come from ServerHello; observing ServerHello does not prove handshake completion or successful delivery.
  • TLS 1.3 certificates are encrypted. Chain validation requires visible certificates, observed SNI, capture time, and SMS_TRUST_STORE. Revocation is not checked.
  • Capture SHA-256 and report hashes support integrity comparison, not source authentication or digital signatures.
  • Analysis reflects strictly traffic captured and visible within the submitted packet capture window.
  • Passive network observation cannot evaluate email clients or cryptographic capabilities absent from the capture.
  • Incomplete TCP streams or truncated TLS handshakes in capture boundaries may limit full capability assessment.
  • AI-assisted anomaly prioritization is relative strictly to the observed client population in this capture.
  • AI anomaly engine abstains from statistical ranking when the comparison population is insufficient (minimum 5 observed clients).
  • Encrypted application-layer email payload (message text, headers, attachments) is not decrypted.
  • Hardening Impact Simulation results reflect passive capability evidence only and do not modify live servers.
